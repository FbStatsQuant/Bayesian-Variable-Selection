1. **[blocking] Truth cannot be restored in one call after a successful mode-000 lock.** File: `code/lowp/R/lowp_seal.R:87–92` (also the promise at lines 15–17).

   **Evidence:** The unlock branch enumerates descendants before reopening the top directory. On Linux as the ordinary owner, a mode-000 `truth/` cannot be traversed, so that enumeration cannot discover its locked `p0020/`, `p0030/` directories and files. The call reopens the root but leaves descendants locked. I exercised the unchanged function with a small, explicitly mocked POSIX filesystem: lock produced modes `000/000/000`; one unlock produced `755/000/000` for root/subdirectory/file. See scratch `truth_unlock_model.txt` and `review_checks_final.log`. This is a model of POSIX traversal, not a Linux execution; the actual Windows function correctly refuses mode-000 operations. `Sys.chmod` return values are also ignored, and the function returns TRUE even if a permission operation fails. The sealer likewise ignores the result at line 69.

   **Fix:** Restore the root first, then discover and restore each directory before descending; finally restore files to 0444. Alternatively retain a checked inventory outside the locked tree. Check every chmod result and verify the resulting modes. Require an ordinary-user Linux lock/unlock/access test in the pilot, covering both production and dev truth trees; the Windows read-only test is insufficient.
