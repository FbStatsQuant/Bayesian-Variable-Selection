## Issues costing points

1. **Numerical-oracle explanation overstates the sufficient condition — minus 0.4.** Location: numerics/README.md:9-12, the sentence beginning “Integer tables (|values| < 2^53 …) make every partial sum exact in binary64.” Representable integer inputs alone do not guarantee representable partial sums: (2^53-1)+2 is already a counterexample with both inputs below 2^53. The actual supplied families are safe: for example, run_checks.py's widest integer family has p<=12, block scores of magnitude <=30 and prior magnitude <=5, bounding every score sum by 365; lemma_probes.py uses BIG=10^9 with small bounded scores. **Fix:** replace the general assertion with an explicit bound on every relevant partial/prior sum for the tested families (or state and check a sufficient sum-of-absolute-values bound <=2^53). Keep input representability and sum exactness as distinct requirements. No rerun failure or theorem counterexample results from this wording defect.

2. **Version/hypothesis summaries lag the locked statement — minus 0.3.** Locations: PROOF.md:3 and its hypothesis column for the frozen-code clauses; lemmas/L1_reduction.md:5; L5_enumeration.md:34; L6_assembly_and_deviation.md:6; LFP_floating_point.md:3-4. These still point to v1.1, or list only H1-H3 without the added execution hypothesis H4, although STATEMENT.md is locked v1.2 and the operative lemma statements now include H4. This is an avoidable ambiguity for a reader checking precisely which theorem was proved. **Fix:** update current target/notation references to v1.2 and add H4 to the proof-index rows and L-FP summary that assert behavior of the frozen C++. Historical descriptions of earlier versions may remain. The proofs themselves already fit the v1.2 theorem, so this is not a missing mathematical assumption in the current target.

These are the complete point deductions. I found no blocking issue in (a)-(f).
