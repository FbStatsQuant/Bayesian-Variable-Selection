## Bounded-scoring correctness

The implementation's strict inequalities are correct. The abbreviated comment at lines 169–174 needs the following equality argument: `position <= e <= fmin` alone would not imply `position < fmin`.

- The pre-scan runs serially before any phase-A tile and initialises each particle's bound to its earliest changing/failed **member** after `q`, or `UINT32_MAX`. The deletion test exactly preserves `ODDS_FAILED < 0 || !(u < odds)` and the addressed uniform. A member at the bound is cached and its row entry is always written by its owning tile, so it does not need the non-member scoring mask.
- During phase A, the only decreases of a bound are to changing/failed additions whose own tiles have already scored them. For a consumed non-member `j`, at its tile's score-time bound either `inv[j] < bound`, or equality would require that bound to originate from `j` itself. The latter is impossible before `j`'s unique tile scores and scans it; the pre-scan bound belongs to a different, member label. A bound below `inv[j]` would imply an earlier change and prevent consumption of `j`. Therefore every consumed non-member passes its particle's mask. OR-ing these masks over the support's particles is sufficient.
- The bounded scan uses `q < position < best`; it can omit the cached deletion at `best`, and any already established event remains represented by `fmin`. A tile's scan also loads `best` after its score-mask loads in the same thread, so atomic coherence and monotonicity make its candidate mask a subset of what that tile scored, even for candidates not ultimately consumed. The walk can only shorten consumption via an earlier U/N/I event. Phase B correctly uses `q < position < e + 1`, hence includes the changing position. The multi-particle path preserves counts, smallest particle and position provenance; the one-particle path visits labels in ascending order.
- Empty supports have no deletion bound and start at infinity. For `k = K` / `!add_ok`, infeasible additions still get `(NaN, 0)` and use the dense scan. Non-fast supports also retain dense scoring. Score ties do not create position ties: orders are permutations, and all acceptance tests preserve the original strict uniform comparison.
- Packed score lanes have independent arithmetic. Bit lanes are grouped by insertion position before each call, every valid lane is filled once, and repeated padding lanes are never stored. Products preserve the accumulation sequence; Philox uses each lane's own position. Range comparisons are unsigned in both the AVX-512 and scalar implementations. Tiles are multiples of 64, range chunks are aligned to 16 positions, and zeroed tail bits prevent the final partial tile from producing out-of-range labels. At `p = 1,000,000`, `m = p + 16` and `e + 1` fit in `uint32_t`.

## Concurrency, contracts and scope

No new data race was found by source inspection. Each tile has one owner for its disjoint score-row columns; inverse orders, support caches, `q`, and support membership are immutable during phase A. Relaxed atomic `fmin` updates implement a decreasing minimum; a later scan load in the same thread cannot precede its score-time load in that atomic's modification order. Stale cross-thread bounds can cause extra scoring, not missed required scoring. Phase A's parallel-region completion precedes the walk and phase B. Phase-B tiles own distinct `rb_cur[j]`; ledgers/scratch are per thread, and counter additions are atomic. The mutex protects failure reporting. This is inspection plus invariance testing, not a ThreadSanitizer claim.

`bounded_scoring` is absent from [fingerprint()](/home/fb31/.t3/worktrees/Bayesian-Variable-Selection/t3-6650c0f6-4f3b6d12e45d22f8/Scripts/SMC_BVS/engine_v4/src/island/island_run.h:347), as required for an execution parameter. `KernelStats` is excluded from the law-output hash. No changed file is outside `engine_v4/`, no reference `core/` source or arithmetic flags changed, and no large binary was added. K1 keeps the existing O(G p) score/order memory and dense product calculation; no new p-squared storage or 1M integer-overflow issue was found. Its small scratch increase is per thread/per tile; the PR's claim of zero memory-plan delta does not mean zero added allocation (finding 1). Production-setup/SPR performance remains a separate pilot gate; the stand-in benchmarks cannot validate it.
